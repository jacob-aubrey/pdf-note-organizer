The selected preview policy retains images for drawings and handwriting only. Highlights/typed notes retain text, comments and PDF page links. Extraction and both Word layouts follow this policy, including cached old entries. Highlights without a text layer point to the source PDF. The history view omits image payloads while keeping the saved history intact.

At inspection, the database occupied approximately 601 MiB. Active highlight image payloads accounted for 259 MiB, drawing images for 17 MiB; database history and overhead add further storage. This follow-up reviewed the combined sorting, PDF notes, paper-linking, storage, transfer, and interface workflows. ### Confirmed defects addressed

- **Partial preferences saves:** Inbox configuration/key changes and review invalidation now share a transaction with viewer, processing-default, and Connections changes. Cached settings are published after commit. A failed save leaves the previous settings/key intact and keeps the draft open. Watcher restart problems after a successful commit are reported separately. Running commits are distinguished from work cancelled during shutdown.
- **Interrupted filing:** Startup recovers durable copies before returning pending PDF handoffs. A normal refresh delivers newly recovered filings once. Uncertain filing errors remain saved and are visible through **Filing recovery…**, including source and destination paths when the incoming file is missing.
- **Final Inbox removal:** Source and destination are held under nested Windows sharing guards while their hashes and the reviewed source signature are verified. The source is deleted through that verified handle only while a complete destination stays protected. Concurrent source/destination edits or replacement cannot remove the last complete reviewed copy. Published copies are also retained when an Add files or filing source changes.
  Retryable source-deletion failures retain their journal state, expose a saved reason through Filing recovery, and avoid repeating unchanged notifications. A successful automatic retry clears the issue.
- **Stale document review:** A preparation worker checks the naming-settings generation under the controller lock immediately before saving its result. A settings change cannot publish the earlier proposal as a completed review. Filename-format-only changes can reuse the extracted details.
- **Annotation identity collisions:** Annotation identifiers now distinguish pages and repeated identifiers within a page. The extraction revision triggers one refresh of older saved PDFs, without editing their source bytes. Separate notes and histories remain associated with their source rather than being treated as one mark merely because their PDF identifiers match.
- **Paper relationships and review decisions:** Current paper links record enough membership history for **Undo last link…**, with later changes checked before restoration. Legacy links have no equivalent undo snapshot. Search, finding/state filters, column sorting, **Keep separate**, **Review again**, and source-opening actions make existing-library review manageable in small batches. These actions do not remove physical PDF copies.
- **Moved watched folders:** **Locate moved folder…** reconnects an existing moved collection while retaining saved notes, history, settings, and related saved paths. It does not move files. Affected queued transfers require destination review rather than silently using the previous route.
- **Managed PDF replacement:** Windows replacement protects against a file being edited or replaced after verification, and preserves available complete copies when publication or cleanup fails. Retained `.preserved` paths are recorded. Library's recovery count and **View sync details** expose those paths across later launches, including when the new PDF saved but previous-copy cleanup failed.
- **Notebook publication:** The final save now uses the same guarded publication mechanism for generated Word documents. A file created or edited during the last save boundary is retained rather than overwritten. Existing edited-notebook backups remain supported. The saved generated fingerprint comes from the staged document, so an edit made immediately after publication is recognized as a user edit on the next export. Any complete previous copy retained after cleanup failure is reported by its exact path.
- **Outgoing transfers:** Lost confirmation can be reconciled using saved transfer identity rather than creating an unrelated second paper. Retry checks the current file, linked root/source, and destination. **Retry selected…** explicitly accepts changed contents or routing; **Cancel selected transfer** stops future attempts without deleting local files or an already committed cloud item.
- **Interface guidance:** Folder opening is available in Library and Notes. The footer navigates to the log, Library's Show/Hide controls toggle it, selected-folder mapping is labeled **Map and sync…**, and column-divider double-click fits content. Popup placement uses the selected monitor's work area instead of assuming one screen. README now separates setup, ordinary use, gradual cleanup, recovery, and technical reference.

## 2026-10-11 — Notable 2.4.0: one PDF view with PC and tablet notes

This change implements the approved combined view. Opening a paper in Library or Notes prepares one PDF with its PC annotations and retained reMarkable annotations. Export annotated PDF saves that view to a separate, chosen location. There are no source visibility switches. This is a source release; no executable was packaged. Development and verification used disposable libraries, synthetic papers and simulated cloud responses. The user's research folders, normal saved library and live cloud account were not changed.

### What is stored and what is checked

- A successful cloud sync uses a matching ordinary PC PDF, or publishes the original tablet-imported PDF under its ordinary filename if no PC counterpart exists. It no longer publishes a permanent `[reMarkable ID].pdf` reading copy in each research folder. Ambiguous candidates, independent annotated tablet copies, edited old reading copies and conflicting destinations remain for review.
- The app retains an unchanged tablet baseline, separate tablet layers, and immutable source records for each saved cloud revision. Identical baselines share private storage. This removes routine visible reading copies, but does not promise that every original is stored only once: a private recovery baseline can duplicate a user-owned PC file, and history uses storage too.
- PC and tablet notes keep separate source identities and saved histories. Tablet extraction excludes native annotations already carried in the imported baseline. Moving old saved records to the private identity and saving the new notes share one database transaction. Failed extraction leaves the earlier notes intact. Folder membership changes that cannot preserve the relationship remain for review.
- Combining requires the same physical page order, page geometry and printed content. Exact page content/resource checks include inherited resources and optional-layer visibility; otherwise exact annotation-hidden rendering and structured text are compared. Different editions, changed flattened marks, inserted/reordered tablet pages and uncertain format support stop the operation. Harmless but unproven PDF rewrites can also need review.
- Original PC bytes and tablet source bytes are never rewritten to make a combined view. The disposable output uses the current PC annotation layer and adds tablet marks. Native annotations in the tablet's imported baseline must still be present unchanged on the same PC pages, including repeated marks, appearance streams and embedded annotation data; missing or changed imported notes require review. Additional PC notes are allowed. An already inherited tablet mark is suppressed only when its stable identity and full signature agree. A conflicting PC edit of that same mark requires review.
- Reading PDFs are prepared in the existing PDF process, off the interface thread, and cached privately with a normal 128 MB budget. Only verified unchanged cache files are eligible for automatic eviction. Edited, unknown or currently protected files stay; the current large view can temporarily exceed the budget. Export refuses to replace an original or registered source and binds replacement of an earlier export to the exact bytes confirmed by the user.
- A failed newer source download/conversion/adoption cannot silently advance a good combined view. Offline reconstruction and local settings refresh use the accepted cloud revision explicitly. Losing cloud visibility preserves any unresolved conversion/conflict classification, saved notes and sources.
- If note migration commits just before the sync record fails to save, the next attempt recovers the same document identities and history from the private record. It does not recreate the retired reading-copy source or lose the evidence needed for reviewed cleanup.

### Existing reading copies and Word notebooks

Migration retains existing extra PDFs until the user opens Library → More → Review extra PDFs. The planner checks app ownership, unchanged bytes, retained source integrity, ordinary-primary identity, saved document/source IDs, note history and current generated notebook links. Cleanup rechecks the reviewed evidence under a database write lock and Windows file guards before removing only the selected old copy. Edited, uncertain or still-dependent copies stay with an explanation. Notes, originals and source history are not deleted by this action.

An older reading copy can qualify when its exact historical tablet revision is retained and its imported baseline matches the accepted paper. The immutable historical source record, baseline and layers are guarded during removal. Unknown revisions, changed historical files and a different baseline remain blocked.

The cleanup dialog names each path, explains blockers and asks for a separate final confirmation. It also requires acknowledgment that links in older personal exports or notebook backups may still refer to the removed file. The app cannot discover every such external document. Current generated notebooks must have refreshed links before a copy becomes eligible.

For migrated papers, generated notebooks combine PC and tablet notes under the paper and physical page. Their PDF links point to the ordinary original, rather than a temporary combined cache file. Those original links can omit newer tablet marks; Open PDF and Export annotated PDF provide the combined page. Unmigrated legacy notes keep their existing source links until migration succeeds. The reMarkable review action opens its retained review copy directly so the user can inspect a conflict even when the combined reader correctly refuses it.
