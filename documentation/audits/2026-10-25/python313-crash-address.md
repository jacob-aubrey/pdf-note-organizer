# Packaged Python crash-address evidence

The exact Python 3.13.1 AMD64 DLL from the first 0.8.5 worker maps the Windows fault RVA `0x2af768` to **`dump_frame + 0x34`**. Windows DbgHelp loaded the official matching PDB with `SYMOPT_EXACT_SYMBOLS` and returned `D:\a\1\s\Python\traceback.c:898`, displacement 0. The instruction is `48 8b 46 70` (`mov rax, [rsi + 0x70]`): the code-object filename read after writing the `File` prefix. Function bounds are RVA `0x2af734–0x2af883`. Exact DLL/PDB/archive hashes and bytes are in `python313-crash-address-evidence.json`.

The PDB came from [Python's official 3.13.1 AMD64 core symbol archive](https://www.python.org/ftp/python/3.13.1/amd64/core_pdb.msi). The MSI was opened read-only through Windows Installer database APIs, and its embedded cabinet was extracted into the audit temporary directory. Nothing was installed. The first download escalation was not executed because automatic approval review hit the account usage limit; it succeeded after the parent reported credits renewed.

This confirms the failing function belongs to native traceback dumping. It does not recover the faulting process's registers or prove the precise lifetime of the invalid object. The fact that another Python thread was in an HTTP/socket call is not evidence that HTTP code caused the native access violation.

Upstream [CPython issue 140815](https://github.com/python/cpython/issues/140815) documents crashes in the native faulthandler watchdog and the [3.13 backport](https://github.com/python/cpython/pull/140985) adds invalid/freed frame and code checks. The [official 3.13.10 release NEWS](https://raw.githubusercontent.com/python/cpython/v3.13.10/Misc/NEWS.d/3.13.10.rst) includes that change (release December 2, 2025); the shipped 3.13.1 predates it. This is a strong relevant upstream lead, not proof that this particular production event is the exact same race.

A later [open upstream report 158200](https://github.com/python/cpython/issues/158200) describes a native watchdog race involving freed code metadata on a different Python branch/platform. It supports treating native timer stack walking as best effort; it does not establish a Windows 3.13-specific fix or demonstrate that updating alone eliminates every watchdog race. The [faulthandler documentation](https://docs.python.org/3.13/library/faulthandler.html#faulthandler.dump_traceback_later) confirms that delayed dumps use a watchdog thread and require the output file to remain open.

No production data, credentials, or live sync retries were accessed for this investigation. Backend owns the isolated reproduction attempts and the final safe Python sampler repair; the frontend reviewer separately verified the first 0.8.6 package with that sampler enabled during 53 synthetic native/OCR checks.
