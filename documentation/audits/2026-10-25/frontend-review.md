## Findings

### F1 — Citation lookup UI promised a fallback that is intentionally disabled (P2, repaired)

`zotero-support/ui.js:1108` names “Zotero’s normal PDF recognition service” in the import checkbox; line 1122 says the fallback sends initial PDF text to that service. However, `zotero-support/library.js:116-119` explicitly avoids `RecognizeDocument`, creates a generic local reference when no title-verified DOI candidate exists, and adds a citation warning at line 133. The controller regression explicitly asserts zero recognitions for rejected DOI metadata. The setup documentation repeats the outdated fallback description.

Consequence: the visible enabled choice suggests that citation fallback is available for PDFs without a usable DOI, while the final implementation deliberately does not run it. This is a current capability/copy mismatch; it does not demonstrate data loss. Align the checkbox/help/setup documentation with the title-verified DOI route and manual citation review, or implement and validate a guarded metadata-only fallback before promising it.

Repair: the import checkbox now says “Retrieve citations using title-verified DOI metadata.” Its help and `documentation/ZOTERO_PLUGIN.md` describe the retained local reference and manual citation review when no matching DOI metadata can be verified, and accurately state that this route does not send PDF text to Zotero's recognition service. Recognition was not enabled. The scan-privacy controller regression uses the new label and continues to verify that changed lookup settings require a rescan.

### F2 — Automatic runtime health check verified only the executable (P3, repaired; conditional packaging route)

`tools/build_zotero_support.py:17-25` accepts a runtime directory and lists every DLL/model/other member. `zotero-support/ui.js:137-139` declares a previously extracted runtime healthy when its ready marker and executable hash match, without checking the other manifest members. `tools/test_zotero_ui_recovery.cjs:175-197` covers a missing/corrupt executable, not a healthy executable with a missing DLL. An isolated invocation of the actual `launch()` with a healthy EXE, existing ready marker, and absent `_internal/essential.dll` launched the helper and repaired zero files (two manifest members).

Consequence: a directory-style runtime whose secondary DLL/model was removed or corrupted is not repaired automatically. The current 0.8.4 package has only one manifest member, so this condition does **not** affect that package's extraction verification. The explicit “Repair bundled helper” action forces extraction and remains a workaround. Check every manifest member for supported directory runtimes or narrow the packaging contract to a single executable.

Repair: `launch()` now checks existence and hash for **every** runtime manifest member before reusing the ready marker, then uses the existing verified extraction path when any member is absent or changed. Existing path validation also runs before these health probes. The controller suite covers missing EXE, corrupt EXE, missing DLL with healthy EXE, corrupt DLL with healthy EXE, and reuse of a completely healthy runtime without extraction. All four JS syntax checks and all five controller suites pass after both repairs; `git diff --check` passes for the edited files. The original finding references above describe the pre-repair line positions.

### F3 — Audit polling could read a partially written response (P3, harness only, repaired)

During the 0.8.5 rendered UI audit, `tools/test_zotero_plugin_live.py:421` attempted to JSON-decode an empty `response.json` while the test extension was writing it with `IOUtils.writeUTF8`. The traceback occurred before a layout assertion. The unchanged checker passed on retry. This was a test transport reliability defect; the shipped plugin and its JSON-line worker transport were not implicated.

Repair: the response polling read catches only transient `JSONDecodeError` and continues under the same 135-second deadline and command identity. Valid matching error packets still raise their original error and stack. `tests/test_zotero_live_transport.py` has **three passing isolated regressions**: empty/partial packets followed by a stale command and then the matching packet; persistent malformed JSON still reaching the original deadline; and valid matching error packets being reported immediately. The first test invocation was blocked by sandbox TEMP-directory permissions; setting TEMP/TMP to an audit-owned workspace directory allowed all three tests to run. The harness is not bundled, so this repair does not alter the 0.8.5 XPI hash.

### F4 — Cached PyMuPDF diagnostic output can terminate the JSON helper session (P2, confirmed)

The pinned PyMuPDF dependency caches its default message stream as `sys.stdout` at import (`pymupdf/__init__.py:164`), and `message()` subsequently prints to that retained stream (`:274-275`). The worker's per-request `redirect_stdout(sys.stderr)` therefore does not capture those messages. PyMuPDF is imported by the worker's PDF modules before dispatch. This behavior is documented by [PyMuPDF's diagnostics documentation](https://pymupdf.readthedocs.io/en/latest/app3.html#diagnostics), including the supported `PYMUPDF_MESSAGE` and `set_messages()` routing controls.

Independent reproduction used generated PDFs with content stream `q garbage Q` or `/MissingXObject Do`; `get_text()` and `get_pixmap()` emitted MuPDF error diagnostics plus blank lines to stdout under `redirect_stdout(stderr)`, although processing returned normally. With the default launch, the two cases produced eight non-JSON stdout lines and no stderr output. With `PYMUPDF_MESSAGE=fd:2`, stdout contained only the expected JSON markers and all 266 diagnostic bytes went to stderr. Evidence: `pymupdf-stdout-repro.json` and `pymupdf-stdout-routing-results.json`.

The real controller's `launch()` JSON reader was independently exercised with the exact captured MuPDF line followed by a valid matching JSON packet. It killed the synthetic child, cleared the process, and rejected the pending request with the generic helper-stopped label; the clean-JSON control resolved without killing. Evidence: `frontend-transport-noise-repro.cjs` and its JSON result. This proves a recoverable PDF diagnostic can interrupt the plugin session. It does **not** establish that the same diagnostic caused the separate production 0.8.6 interruption; no offending production stdout packet was captured.

Frontend repair: helper launch explicitly sets `PYMUPDF_MESSAGE=fd:2` before any import, using the dependency's supported environment control. Malformed JSON remains fatal; a fixed invalid-response label now distinguishes that condition without logging the offending line, document text, or credentials. The controller regression asserts the environment and continued strict malformed-packet rejection. All four frontend syntax checks and five controller suites pass. Backend owns the additional direct-worker message/log routing and its subprocess regression; final package validation follows that source freeze.
